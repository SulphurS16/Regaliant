# 2. From boot to a presented frame

## Before the guest entry point

The Windows launcher manages game selection and verification, settings, shader preparation, save backups and recovery. Its source separates display, saves, shaders and UI. Linux exposes a command-line path. The runtime accepts an app directory or a readable-in-place `.zar` archive, so loading a level need not unpack a second game tree. The runtime and launcher have separate platform entry points. On Linux the game source remains read-only, persistent player data goes under the XDG data directory, and disposable logs and shader stores go under the cache directory. [Launcher](../../crates/launcher/src) · [Linux paths](../linux.md)

The guest modules are `eboot.bin`, `sce_module/libc.prx` and `sce_module/libSceNpCppWebApi.prx`. In `sce-elf`, a `Module` represents a parsed ELF64 image or supported SELF wrapper. Program headers (`Phdr`) describe loadable ranges and permissions. `DynamicInfo`, symbols and relocation entries (`Rela`) describe references whose final addresses the loader must install. The runtime maps segments, supplies thread-local storage, resolves references against module exports and the HLE registry, and patches supported instruction sequences. The HLE `Registry` indexes by library and NID, the console's encoded symbol identifier. Its `Export` records address, readable name and whether the symbol denotes data. An imported variable must receive usable storage just as an imported function needs a callable address. [Parser](../../crates/sce-elf/src/lib.rs) · [Loader](../../crates/runtime/src/loader.rs) · [Registry](../../crates/runtime/src/hle/linker.rs)

Once the guest starts threads and fibers, several producers can change memory at once. Kernel HLE supplies memory, file and synchronization operations. Library modules supply services including Agc graphics, VideoOut, Audio2, controller/device services and savedata. Save transactions, asynchronous reads and queue completion all have observable boundaries. A host call returning early is safe only if the guest sees its completion at the promised point. The Linux APR and save-read fixes in `339c26d` illustrate how a successful-looking short read can violate that contract. [Kernel](../../crates/runtime/src/hle/kernel) · [Libraries](../../crates/runtime/src/hle/libs)

## What an address identifies

`mem.rs` reserves a guest address range starting at 16 GiB. Reservation claims address space. Commitment supplies accessible backing. `MemState` keeps virtual mapping records (`Vma`) and direct-memory allocation records (`DmemBlock`). Direct memory models console physical ranges. The same physical range can outlive a virtual mapping and appear at two virtual addresses. The section-backed path maps direct memory by physical offset in one backing object and allocates offsets for other memory in a second. Views use 16 KiB granularity. Write tracking inside them uses 4 KiB pages. [Memory manager](../../crates/runtime/src/mem.rs) · [Sections](../../crates/runtime/src/sections.rs)

Each mapping also gets an alias view suitable for GPU import. Both virtual addresses expose the same backing bytes. The renderer can import the alias using Vulkan's external host memory interface while the guest view changes protection to detect CPU accesses. Protecting imported pages themselves had lost the device on the RTX 4090. A slot holds an alias address range while old work still references it. Reusing the guest address for new storage can require a different alias slot. This is why the memory manager must inform the renderer of remaps even when the numeric guest pointer does not change. [Section lifetime rules](../../crates/runtime/src/sections.rs)

## Recording one draw

1. The game builds a PM4 command buffer and submits it through AgcDriver. A command-processor thread walks it. Its `Cp` carries context, shader and configuration register state. It follows indirect command buffers, changes state, decodes conditional execution and handles memory and synchronization packets as well as draws. Multiple guest queues can progress independently. [Command processor](../../crates/runtime/src/gpu/cp.rs)
2. For a draw, register state identifies the shader programs and user data. The shader front end caches decoded instructions by program, analyzes where scalar values come from, and follows resource descriptors in guest state. A buffer descriptor describes a range and format. An image descriptor also carries dimensions and layout. `Resolved` and `Prepared` carry the result toward execution. The translator's `Spec` describes choices that can change generated code. A cached program alone cannot identify every valid translation. [Shader front end](../../crates/runtime/src/gpu/shaders.rs) · [Analysis](../../crates/rdna/src/analysis.rs)
3. RDNA instructions operate on scalar registers shared by a wave of invocations and vector registers with values per lane. An execution mask selects participating lanes. Translation must preserve lane operations, memory formats and floating-point corner cases as well as arithmetic. The translator emits SPIR-V with the required bindings and stage interface. The Vulkan pipeline combines stages with state such as render-target formats. Compute dispatches use the same translation machinery with a compute stage. [Wave masks](../../crates/rdna/src/wavemask.rs) · [Translator](../../crates/rdna/src/translate)
4. Each queue's `Exec` records Vulkan commands. Images need views, layouts, and conversions from the console's tiled memory layout where appropriate. A render target can become a texture in a later pass. Fast-clear metadata may stand for a uniform colour or depth without a full pixel write, so knowing which image owns that metadata matters. For buffers, FE2 arranges current data in the sparse mirror described below. Pipeline reuse and speculative recording reduce CPU work only while all the assumptions used to record still hold. [Executor](../../crates/runtime/src/gpu/exec.rs) · [Image cache](../../crates/runtime/src/gpu/images.rs)
5. Queued batches use barriers and timeline semaphores to preserve dependencies. Guest compute queues have their own CP threads. Their batches normally run on the main Vulkan queue. The optional ordered-compute mode can overlap work on a compute-only device queue when dependencies permit. A promised label allows dependent recording to proceed before physical completion if submission still enforces the dependency. When the guest requests a flip, VideoOut and the presenter associate that request with its image. On Linux the renderer presents through a Vulkan swapchain on an SDL surface. A queued guest flip, completed GPU execution and a newly presented image are distinct events. [VideoOut](../../crates/runtime/src/hle/libs/videoout.rs) · [Linux display](../../crates/runtime/src/platform/linux/display.rs)

## How FE2 decides whether to copy

The sparse mirror is a Vulkan buffer addressed by guest offset. Residency code backs its 64 KiB portions on demand from larger device allocations. FE2 records validity per 4 KiB guest page. On a binding request (a *placement*) it checks whether the mirror can satisfy the current queue's read. A *take* queries and consumes dirty-page information. Every reported CPU write invalidates that page for all consumers of the protocol. Clean pages receive the synchronization epoch sampled before the take. A queue can trust that stamp only within its permitted view. On frequently rewritten small ranges an upload can be cheaper than asking. [Residency](../../crates/runtime/src/gpu/resident.rs) · [FE2](../../crates/runtime/src/gpu/fe2.rs)

An upload is recorded in a batch prologue so it sees results after earlier write-backs. A CPU copy taken while earlier GPU work is still pending could restore old bytes into the mirror. GPU stores mark the 32-bit words they changed. A scatter kernel copies marked words back at required boundaries. The optional two-device-queue path keeps separate write bookkeeping for the two queue families. On supported Windows paths, C4 can hold selected pages in the mirror until the CPU needs them. Linux uses eager write-back. The early comments in `cp.rs` and `exec.rs` describe the compute-only milestone. Draw execution, FE2 and ordered asynchronous compute superseded that design. [Front end](../../crates/runtime/src/gpu/fe2.rs) · [Scatter kernels](../../crates/rdna/src/kernels.rs) · [History](03-history.md)

Finally, `pcache.rs` persists driver compilation products across processes, while `hitch.rs` associates unusually long presented frames with overlapping translation, compilation, uploads, file I/O, recording and waits. GPU timestamps can arrive several flips later. This lets a profile distinguish expensive CPU recording from a GPU batch that actually ran long. Overlapping spans alone do not prove which one delayed presentation. [Cache](../../crates/runtime/src/gpu/pcache.rs) · [Hitch accounting](../../crates/runtime/src/gpu/hitch.rs)

## A frame in flight, seen from both ends of each queue

Follow a gameplay frame that draws GPU-driven geometry and displays the result. The walk below uses the structures on the Linux branch. Cost examples come from several explicitly identified scenes and revisions, since the repository does not contain one trace assigning an exclusive duration to every step of this exact frame. Keep a distinction in mind throughout. The guest submits **buffers of PM4**, the host records **batches of Vulkan commands**, and the host display consumes **images**. There is no one-to-one correspondence between those three units. [Queue entry point](../../crates/runtime/src/gpu/mod.rs) · [Executor](../../crates/runtime/src/gpu/exec.rs)

### 1. The game gives up ownership of a list of commands

The title's rendering code constructs PM4 in guest memory. For the GPU-driven route the CPU can describe a list of draws whose final counts or arguments an earlier compute dispatch produces. At Castlewall, the guest's GPU-driven static meshes accounted for about 45% of commands in one census. Forcing its alternative CPU path lost the meshes (`d539031`). An earlier profile found that the title called the port's own Agc writers for individual dispatches (`7256481`). Knowing where a packet was emitted can identify a producer. It does not make the final result of a preceding GPU cull available earlier.

On the host side a `Submission` contains buffer address/size pairs, a queue-local sequence index, timing and optional diagnostic copies and hashes. In ordinary play the renderer is passed guest addresses. Its self-check mode can retain original words, which helps distinguish “the decoder misread the packet” from “the guest rewrote this buffer before the reader got here.” The process-wide `QUEUES` mutex protects the collection of queues. Each `Queue` has its own `pending: Mutex<VecDeque<Submission>>`, work condition variable and separate completion notification. Enqueuing on graphics does not require holding a lock on every compute queue's pending work. The submitted and done counters also allow throttling a producer that has run too far ahead.

### 2. A host CPU thread reconstructs the graphics state

The queue worker called `gpu-gfx` owns the graphics `Cp`. A compute queue has a sibling named for its ID, for example `gpu-acb0x50`. The CPU time attributed to these threads is time decoding, preparing, recording or waiting on the PC processor. The device's execution time appears separately in GPU timestamp queries. Each worker processes its queue's submissions with remembered state. An indirect draw that changes only the arguments can inherit previously installed shader registers, render targets and user data. Discarding state at the submission boundary would require the game to repeat setup it never promised to repeat.

The CP reads packet lengths and opcodes, updates its register banks and interprets synchronization. Some packets imply host-visible work. A write of a label used by a waiting CPU thread cannot be reported as done simply because the decoder has seen the packet. Other packets form runs that can be planned and recorded concurrently. Workers named for the parent queue with a `-parN` suffix can each own a recording executor. They operate on chunks with appropriate starting state. Recording a later chunk early does not authorize submitting it first. If a speculative path discovers a memory read or action that invalidates its assumptions, the CP may have to stop, settle the preceding work or discard that recording. [CP](../../crates/runtime/src/gpu/cp.rs) · [Recording workers](../../crates/runtime/src/gpu/par.rs)

A recorded replay helps put “parallel” in perspective. On 12 October its GPU was busy for 49% of the interval and the graphics CP spent 40 of roughly 52 ms per replay frame recording while the device had idle opportunities. Some of the longest gaps came from the main CP's own part of a parallel run (`7b94e6c`). On another day, 128-command runs helped Doran by 2% but cost 2% on a walk (`af99a6e`). Larger chunks save setup and cross-thread messages, while smaller chunks can share uneven draw costs more evenly. Those measurements did not justify selecting one new size for all games or even all areas of this game.

### 3. Preparation finds the bytes this specific draw will use

A shader address identifies instructions. The registers and the descriptors reachable from the registers identify this invocation's inputs. The front end resolves chains of scalar loads into guest ranges, decodes buffer/image records and builds the stage's specialization. One useful profile found roughly 64 words in fifteen separate ranges per stage, and the walk through constants and descriptors took about 60% of preparation. Prefetching those lines first made no measurable improvement (`a37fe47`). At the vista some particle preparations reached 254 words in 67 ranges and fifteen resources. Indirect dispatches for these particle programs accounted for about 17% of front-end CPU in that census (`af99a6e`). Counting unique shader binaries alone would conceal this recurring per-use cost.

Preparation can find a decoded program or translation in memory, obtain a matching recorded translation, or invoke the translator. Pipeline lookup then has its own synchronization. For example the compute path's `PIPE_FLIGHTS` map tracks in-progress creation and `PipeFlight` carries a result protected by a mutex and condition variable. A second requester can discover the same outstanding compile without requiring two costly driver calls. The asynchronous job queue, its condition variable and queued/failed sets make “work requested”, “object ready” and “creation failed” distinguishable. Much of this path disappears on a true warm hit. A single cold pipeline on a dependency chain can still dominate a frame, as the two particle compiles in `200bc91` showed. [Prepared stages](../../crates/runtime/src/gpu/shaders.rs) · [Learned pipelines](../../crates/runtime/src/gpu/precompile.rs) · [Pipeline flights](../../crates/runtime/src/gpu/exec.rs)

### 4. Placement and recording establish the draw's prerequisites

The executor needs a buffer plus offset and length suitable for binding. It consults the guest mapping and mirror residency, then FE2's validity information. Recent lookups can answer immediately. A miss may need a mapping lookup, a take and a scheduled upload. These have quite different costs. In the 16 November Castlewall measurements a placement memo hit took 32 ns and a miss 966 ns, with misses amounting to about 20 ms per flip (`682c219`). In a separate November profile, waits occupied about 31% of graphics CP time, write-watch queries about 4%, and mapping lookups 4–4.6%, including about 3% in the lock on misses (`3b3126d`). These are measurements at different boundaries. Adding the lock share again to the lookup share would double-count it.

On Linux a mapping guard lets scans for independent pages run concurrently while keeping a remap exclusive. Another mutex protects write-watch bookkeeping, including the explicit host-write journal. On the image side an upload can require reading and detiling guest pages. In the original Windows crash the texture reader checked a streamed array, then a title thread unmapped one of its layers before the read. `GUEST_READERS` held shared across the check and the read, with decommit exclusive, closed that gap (`329c3b7`). The common pattern is a lifetime guarantee extending over the *use* of the address. A cache of previously checked addresses is insufficient by itself.

The recording `Slot` holds command buffers for the applicable device queue families, a descriptor pool, fence, last sequence and optional buffers for scalar parameters, snapshots and timestamps. Its resources can be overwritten once the previous device use completes. If all eligible slots are in flight the recorder waits. This is one reason a thread sampler showing time in a condition variable may be evidence of a busy GPU. In the Palace profile of `7a5b73c`, about 5 ms per frame went into waiting for slots whose device work was still running. Sixteen slots yielded 38.7 fps versus about 39 for the baseline. More space for queued work did not make the device finish it sooner.

### 5. Submission turns the recorded dependencies into device work

A `Batch` has a sequence, a fence for GPU work, a queue-family flag, deferred actions, verification checks and labels the device will write. An action-only entry can have a null fence. The submission worker `gpu-submit` drains jobs from `SUBMIT_Q` under its mutex, sleeping on `SUBMIT_CV` while empty. Preparing the calls in order allows compatible submissions to go together. A highest-submitted sequence and notification keep completion from waiting on a fence for work that has not reached Vulkan yet. Approximately 220 batches per courtyard frame and about 7% of busy graphics-CP samples in queue submission motivated taking those calls off the CP. Two in-run comparisons measured a 1.013 throughput ratio (`e0e221a`). The modest net change makes sense once submission overlaps other activity. [Submission, batch and slot definitions](../../crates/runtime/src/gpu/exec.rs)

The device now sees uploads, dispatches, barriers and draws. At the branch tip, the ordinary path submits graphics and compute batches to the main device queue. The earlier ordered-compute design is still available when requested at device creation and supported by the device. In that mode the two device queues have separate progress timelines. A consumer of a promised label, indirect arguments or overlapping written pages must still wait for its actual producer. A shader reading an image through one description after another shader wrote it through a different view adds an image ownership and layout problem. As a concrete scale, the InsideL Village main-queue trace recorded 5.8 ms of title compute and 4.6 ms of draws, plus about 3.6 ms of port work, including 1.9 ms of CP writes, 1.1 ms of prologues and 0.55 ms of fills (`2fae7f6`). At Castlewall an earlier trace attributed roughly 152 write-backs, 5.4 ms and 49 MB per flip to FE2 (`0e1d420`). These quantities answer different questions. Main-queue totals do not include all parallel compute work, and GPU service time need not lie entirely on the path to the next flip.

### 6. Release, completion and display have different consumers

Once a device queue finishes a batch it can release that batch's slot and collect GPU timestamps. A `Release` keeps the sequence, query pools and reset information for that purpose. Deferred CP effects still need to be published in the order the guest can observe. The common executor has per-device-queue release queues and a `gpu-complete` thread. This separation has a measured origin. In a swamp boot, 10.7 out of 23.0 seconds of accumulated slot waits began with that slot's GPU work already done. Making a reusable main-queue slot wait for unrelated earlier compute effects extended its lifetime unnecessarily. A write to a guest label is different. A consumer can act on it immediately, so publishing it early would violate the very ordering that execution is trying to reproduce. [Release and completion](../../crates/runtime/src/gpu/exec.rs)

Follow the corresponding flip in `videoout.rs`. The port owns registered buffers. `reserve_flip` checks the index and the pending-queue limit, creates a ticket and appends a pending `Flip` with `ready` false. `commit_flip` finds that ticket under the port mutex, makes it ready and wakes the display path. The current buffer and buffers waiting in the flip queue still count as busy when the game asks whether rendering into them is safe. This protocol explains why a capture should identify a particular flip or actual displayed image. Looking up the latest render target after several threads have advanced can retrieve the right scene from the wrong instant. [Flip queue](../../crates/runtime/src/hle/libs/videoout.rs)

In ordinary Linux FIFO presentation, display backpressure sets a further limit on delivery. With optional frame generation, two real display images and their associated inputs can produce an extra host image. A display thread in adaptive mode can repeat the previous image when a fresh one is unavailable. Neither event produces a guest simulation tick. This is the far end of the trace begun by the game submitting PM4. The queue index identifies guest work, the batch sequence identifies host GPU work, the flip ticket identifies an ordered display request, and the presentation counters describe what the application offered for display. A frame-rate number is interpretable only after choosing which of those events to count. [Nexus pacing protocol](../linux-nexus-check.md)
