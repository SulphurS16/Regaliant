# 4. Bringing the runtime to Linux

## 23 November — boot first, then prove what appeared in the window

The first checkpoint (`36c6615`) records execution through engine initialization to `sceVideoOutOpen`. It also records that the intermediate snapshot contained partial renderer work and did not compile as committed. The renderer connection in `3d2e5b3` likewise preceded GPU verification. Separating those observations matters. A loader can execute the title while a defect in swapchain ordering or shader translation leaves the world black.

Linux keeps the host's FS segment register for thread-local storage used by libc and Rust. Supported guest FS accesses are patched to use GS. New threads, fibers and their stacks must see the right guest state while host calls continue to see their own. The virtual-memory layer first reserves a fixed, inaccessible range using `MAP_FIXED_NOREPLACE` and verifies the returned address. Linux implements shared sections using memory-backed file descriptors (`memfd_create`). Multiple shared mappings at the same file offset give the guest view and the GPU import alias the same bytes. [TLS](../../crates/runtime/src/platform/linux/tls.rs) · [Reservations](../../crates/runtime/src/platform/linux/vm.rs) · [Section implementation](../../crates/runtime/src/platform/linux/os.rs)

SDL3 provides the window, keyboard, gamepads and audio output on Wayland or X11. Agc and the shared renderer still produce Vulkan work. Acquire, submit and present must order the image's use with respect to both rendering and the window system (`7bb4114`). The fork separated loading from gameplay timing and removed validation and captures from timed visible-window runs (`1b2a9dd`). FIFO, which presents queued images in order with display backpressure, became the default in `f60016e`. Guest timing remains 59.94 Hz. Later work used physical pixels for the swapchain and pointer coordinates on scaled displays, kept two device audio buffers queued, and enlarged the movie-audio queue (`9278e72`, `66a5bd9`). Render scale and swapchain resolution are separate. A 4K window alone gives no evidence of native 4K rendering. [Display and audio settings](../linux.md)

One dark-scene investigation followed the volumetric scatter shader `cb83739fea041817`. It deliberately stores NaN (a floating-point “not a number”) in invalid slices. Valid slices must reject NaNs left in previous history. The translator began classifying the integer bits for `v_cmp_class_f32` and corrected three-operand median semantics (`6f0b306`). The diagnostic fixture covers an 8×8×72 volume with a known number of finite slices per column. A separate Blackwell experiment found scattered coloured specks with portable translation. The combination of corrected NaN handling and subgroup modes rendered the tested scene correctly. Linux retained subgroup modes on NVIDIA with maximal reconvergence off (`03c5b62`, 24 November). The two changes address different shader semantics. [Maintainer notes](../linux-notes.md)

## 23–26 November — write watch, arming and safe remaps

Windows supplies dirty-page queries. On Linux the initial signal-based tracker protected guest pages using `mprotect`. A CPU store faults, giving the runtime a chance to record the page as dirty and restore write access. Recovery runs on alternate signal stacks. The direct path uses atomics and bounded protection operations. Taking a mutex, allocating memory or invoking Vulkan there could deadlock if the interrupted thread already owned the resource. A remap gate excludes faults that cannot be safely resolved against the current mapping. A fault service thread handles deferred work. Fatal-signal reports and watchdog samples serve a separate diagnostic role. [Signals](../../crates/runtime/src/platform/linux/signals.rs) · [Maintainer constraints](../linux-notes.md)

An alternative introduced in `ebbf5ca` registers guest views with userfaultfd (uffd) for asynchronous write protection. The kernel handles first writes and records which pages have been written without delivering a userspace signal per write. The runtime queries the process pagemap with the `PAGEMAP_SCAN` ioctl to collect written ranges and renew tracking. It also maintains a journal for writes through host paths. For example, the kernel may report EFAULT or a short read when asked to copy file bytes to a protected user page. There may be no guest write signal. Host I/O must stage or disarm appropriately, account for writes, and publish completion after the final copy. An alias must not let a host write escape the protocol. [Write-watch implementation](../../crates/runtime/src/platform/linux/write_watch.rs) · [I/O race fixes, described in the Linux notes](../linux-notes.md)

On 25 November `8d0c5fc` made uffd the default. The tour had crashed three times with corrupted pointers over two stages using mprotect. The same stages completed with uffd. Two races in the mprotect tracker could lose dirty notifications during concurrent writing and re-arming. The repaired fallback has concurrency tests but lacks equivalent full-tour evidence. The full uffd tour produced about 3.1 GB of shader-store data on the tested system. This backend requires kernel support for async write protection and pagemap scanning plus the appropriate permissions. Logs identify fallback. On the I/O side `339c26d` addressed packed APR read-record overflow, unchecked short/error save reads and mapping changes racing host I/O. A stale pointer into reserved address space still needs its missing producer or bad cursor explained.

Correct tracking was expensive. At the Palace roughly 7,300 takes per frame passed through one watch mutex and 99% found no writes. The graphics command processor and four recording workers waited for one another merely to ask the kernel a question. Commit `f83f06a` moved scans outside that mutex while retaining a shared guard against remaps. Registration and the host-write journal still serialize. In the same uncapped native-4K Palace scene, FG off, 31.4 fps became 34.0 and graphics-thread FE2 checks fell from 7.6 to 5.2 ms per frame.

**Arming adds a second way to establish freshness.** A repeatedly clean, quiet page can be made read-only. As long as its armed bit survives, FE2 can skip the next take across epochs. On 26 November `9ca5b66` implemented this in-process on Linux. A Linux signal frame preserves the interrupted code's red zone, the scratch space below the stack pointer, so the Windows debugger-host arrangement is unnecessary here. Arm sets the bit before making the page read-only. Disarm restores write access before clearing the bit. A recoverable SIGSEGV makes the page writable, clears its bit and posts the fault to a lock-free ring. Remapping forgets obsolete page state. Kernel copies disarm first. The uffd tracker still detects writes to pages after an arming fault.

The arming check reported 2.0 microseconds per fault. Two back-to-back Palace comparisons under background load recorded 22.3 to 24.2 and 27.2 to 33.5 fps. FE2 checks fell from 5.2 to 2.0 ms per flip. The branch leaves this opt-in (`DS_LINUX_ARMING=1`). Commit `d41b72b` explicitly keeps C4 off regardless of arming. Detecting the next CPU write and withholding a GPU result until a CPU access are different promises.

The next bottleneck involved section remaps. At about 370,000 pagemap scans a second, scanning workers kept the kernel's memory-map lock busy. Mapping or protecting a view needed the write side. A section commit made four or five such calls under the runtime's remap guard. Four workers once saw one-page checks stall together for 107–108 ms. Commit `21a0f16` maps each Linux view once at its final protection, except when stale bytes need writable access for zeroing. Two old/new Palace pairs measured 28.4/28.8 and 34.1/37.4 fps. Guard hold time fell 18%, with the longest hold down from 27 ms to 4–11 ms. The hitch log now identifies long holds by call site. Adding all four worker waits would overstate the wall time lost by the frame.

## 24–26 November — queue ordering and the shader store

A label wait once woke before the promise of its value had been published. A consumer missing the notification slept until its 1 ms timeout. Publishing and waking in the proper order reduced renderer-thread waits from about 1.06 to 0.03–0.07 ms each, saving about 2 ms per 4K frame in the cited session (`e9a6ffd`). Narrowing waits to an input batch had already hung the GPU and was dropped (`962320e`, `f2b5a2c`). Sparse memory had a separate ordering bug. Sorting bind operations by offset could move an unbind past a later rebind of the same page. Whole-machine freezes coincided with coalescing. A four-minute run with it disabled completed. The optional merger now respects input order (`9f5a3e1`). The frozen system left no kernel message establishing a definitive cause.

The store solves three different problems. A learned recipe tells preparation which pipeline to request. A translated module supplies SPIR-V. A driver binary can avoid costly pipeline creation from source in the next process. Earlier per-pipeline Vulkan caches already addressed a monolithic cache that had grown to 1.5 GB and been rewritten 26 times in a run. The RTX 4090 driver's caches shared a roughly 2 MB block that could be stored once. Current binary replay must additionally preserve pipeline creation flags and compatibility across device, driver, enabled features and translator identity (`6e5ba6f`). Preparation, application binary storage and private driver caches each have separate roles. [Pipeline store](../../crates/runtime/src/gpu/pcache.rs) · [Preparation protocol](../linux.md)

On 25 November one binary refusal stopped blacklisting the entire store. Preparation and play also matched actual device features, including whether presentation-timing extensions were enabled. In a native-4K Nexus second session, source creations in a stationary 30-second window fell from about 260 to zero (`0e64808`). A later failure survived these checks. Two code variants under one key kept replacing each other's file. In one session 49 particle programs cost 83 seconds of compilation, including a 13-second freeze waiting for two compiles. Commit `200bc91` retained variants in sibling files named with their fingerprints. Its salted-key write/read check served all eight pipelines from binaries. That check verifies coexistence; the commit does not give a repeat measurement of the original freeze.

Recording an intent before entering the driver lets the next process identify an interrupted compile. Treating every leftover marker as a permanent failure omitted legitimate draws after a quit or killed run. Since `0084b1d` an interrupted compile gets three tries in total. Attributed driver crashes are tracked separately. A compiler abort on a cube-array texel load had an identifiable translator cause. SPIR-V forbids cube dimension on that fetch operation. A 2D-array view of the same faces permits exact integer texel addressing while ordinary filtered sampling keeps its cube view (`2c7ef52`). [Cube-fetch investigation](../linux-cube-fetch.md)

## 24–26 November — generating and pacing an extra image

Optional FSR3 frame generation began in `1260601`. A native bridge calls optical flow and interpolation on the existing Vulkan queue. Regaliant owns presentation. Interpolation needs two real frames, pre-interface colour (HUDless colour), final colour, depth, motion and matching camera history. Captures occur in guest command order, and a deferred callback must use the command buffer passed at playback. Depth travels through a device-local buffer to preserve bits. The main-view filter prevents a menu character preview from becoming the previous player-camera image (`5919be8`, `9bb44b5`). The fork keeps temporal anti-aliasing (TAA) available to supply inputs even when anti-aliasing is set to Off during generation (`0479087`). [Frame-generation design](../linux-frame-generation.md)

The adapter preserves valid motion vectors. For nonfinite or implausibly large components it tries a neighbour within 2% relative depth in a 3×3 region, then camera reprojection, then zero if the previous projection is invalid. The guest image stays intact. History resets on a missed pair, changed dimensions or excessive age. Render-sized depth and motion can differ from display-sized colour, especially at ultrawide resolutions with the 1512-line internal cap. Fences protect snapshots still used by interpolation. The SDK's own first-use pipeline compiles fall outside the game's preparation tour.

Legacy FIFO pacing can fit 30 real plus 30 generated frames on a 60 Hz display. Adaptive pacing (`418f727`, opt-in) moves presentation to a display thread using completed private copies and delays playback by one real interval plus 4 ms. Empty slots can retain the previous image. The warm Nexus experiment in `0e64808` recorded 39 real fps, 60 fresh images/s with adaptive pacing, one repeated slot and median content age of 38 ms. Those counters describe the application's images. Simulation does not advance on an interpolated image, and an application timestamp cannot measure when the panel emits light. Movies require another clock decision entirely. Commit `b4efb51` presents their 30 fps content on the display's refresh independently of the gameplay limiter. [Nexus measurement protocol](../linux-nexus-check.md)

## The final forty changes, read in development order

The first-parent path follows the fork's own line through merges. At the local tip its last forty commits run from `e35c77d` through `0ee206e`. An ordinary date-ordered log also shows the incoming Windows commits interleaved on 25 November. The account below follows the first-parent path and identifies what the two merges brought across. Several changes were controls, instruments or rejected candidates. They matter because they establish what was actually measured when the defaults changed.

### 24 November — establishing a repeatable frame

The steady runner in `e35c77d` chose a saved scene, native 3840×2160, fullscreen, no upscaler, thirty seconds still and sixty walking. Staying still makes frame-to-frame differences easier to attribute to rendering. Walking makes the title expose new resources and reveals work that disappears at a fixed camera. A separate short session collected diagnostic timing. `d8ff0e0` ensured a recoverable thermal pause did not cancel that diagnosis and added CPU wait spans, write-back timing and allocation counts. The purpose of those extra instruments was to distinguish time on the recording thread from device work and time spent waiting for a dependency.

The automation itself then produced a false stall. A single missed confirm left the game at Continue Offline, so a timed process could be running without ever sampling gameplay. Commit `6ad662f` retried only while that dialog was active, required advancing frames in stable gameplay, and kept separate statuses for uffd, mprotect and the diagnostic session. Blindly sending another confirm later could have selected something in the next menu. The eventual performance comparisons rest on fairly mundane controls like this one.

With a trustworthy route, `962320e` tried waiting only for the batch believed to produce a draw input. That is attractive when older unrelated work has been included in a conservative flush. The candidate hung the GPU and produced device loss. It was removed in `f2b5a2c`, which also tried batching register bookkeeping, reducing payload allocations and caching layout offsets. Steady measurement began logging clocks, temperature and throttling while avoiding pauses inside the route, aborting on sustained 105 °C. The recording candidate showed no gain and was removed in `3dbf4a9`. That commit added graphics-CP sampling, kernel CPU and fault accounting and a shared CPU-work lock. There is no measured successful narrow-wait mode hidden behind these later improvements.

A timeout every millisecond can look much like slow recording when samples are coarse. The label-promise wake candidate in `3dbf4a9` became the default in `e9a6ffd` after the measured per-wait delay fell from about 1.06 to 0.03–0.07 ms. It preserved the producer dependency. What changed was how soon a sleeping consumer learned of a valid promise. This distinction explains how a successful change to waiting could follow immediately after a different change to waiting lost the device.

### 24 November — a microbenchmark win, a startup crash and an invalid speed comparison

Commit `e1d6860` tried caching prepared shader state after validating the guest memory on which it depended. It also changed the leaf size of a FE2 range cache so bindings larger than 20 KiB could benefit. The latter cut a microbenchmark from 37.8 to 12.3 ns per check. Both remained off and were removed in `228c67b`. The microbenchmark answered what happened when that particular check was made repeatedly. It supplied no measurement of the share of gameplay placements covered or the cost of maintaining the candidate in a moving scene.

The startup investigation in `228c67b` captured mappings, instruction bytes, thread and pipeline identity on a fatal signal. The faulting instruction was a deliberate invalid instruction in NVIDIA's compiler while a precompile thread was active. That was a better attribution than assuming any SIGILL in a native port meant unsupported *guest CPU* code. The next commit, `2c7ef52`, found the invalid SPIR-V cube fetch and corrected its dimension. Nine of ten warm-store startups had been crashing. A warm store was repeatedly exercising the bad specialization before the player even reached gameplay. Four affected shader variants passed validation after the change. Durable quarantine protected a subsequent launch from a known fatal compile, while the translation fix supplied a legal pipeline.

`228c67b` also introduced whole-run parallel recording as an experiment. `0fa8e72` required all timed participants to start from the same route-warmed store with a matching translation fingerprint. Its three arms compared baseline, whole-run recording and whole-run plus two candidate improvements. A walking capture showed a green HUD artifact. The later maintainer notes record green geometry, flicker and black pops in motion. Even a favorable timing over that route could not justify the mode: omitting or misordering a draw can make the recorder *faster*. The visual comparison is part of interpreting the number, not a separate cosmetic check. [Recording constraints](../linux-notes.md)

### 24–25 November — verifying each input to interpolation

The first experiment in `1260601` used a native FSR3 bridge and retained the existing window-system presenter. It supplied an extra image between real presentations without issuing another guest flip. Simply loading the bridge did not mean that any generated image existed. In `5919be8` the capture path had failed to recognize both SDR composite shaders, so it never captured the pre-UI colour the SDK required. No context was created. Matching those shaders by code hash and logging the input gates made it possible to see which prerequisite was missing. Adding a required Vulkan feature also rebuilt stored pipelines once.

The next apparent failure was a white image. The saved PNG had preserved an alpha channel used by the SDK as an inpainting weight. The viewer had composited it onto white. Commit `2efc3a7` made display previews opaque and kept raw output alongside them. It also saved previous and current colour and recorded why candidate HUDless captures were skipped. Altering shader exposure or discarding the raw alpha would have destroyed the evidence. `9bb44b5` decoded camera and jitter per frame, checked motion-vector units and sign, and reset history across scene changes. Its comparison against the arithmetic mean of two real frames gives a numerical regression reference. The mean is not the image a moving camera should physically see halfway between them.

The upstream merge `35739da` carried in 21 commits since 0.1.3. It retained both upstream's in-flight pipeline tracking and Linux's driver quarantine, alongside the fork's NVIDIA shader policy. Add-on discovery kept Linux path protections. The Linux port gained the save picker and excluded preview TAA passes from frame-generation history. A small character preview can use the same kind of temporal pass as the main view, but its camera and dimensions are unrelated. An interpolation snapshot must belong to the actual frame being presented.

### 25 November — a completed tour stage, a bad pointer and the visibility of a write

The supervisor was repeatedly replaying the new game on subsequent preparation runs. In `05e0488` the stage's completion message existed in the game log while the supervisor looked for it on standard output or error. Reading the shared health record, validating its stage and tour part, and recovering an earlier successful new-game marker gave “resume” a durable basis. An exit status alone can be consistent with a short orderly shutdown before the work finished. Tests covered stale records and teardown failure.

During the level tour a job worker attempted to read four bytes at cursor 0x55fffe with zero bytes available. The read crossed into reserved guest memory. Commit `d3d3c3f` recorded stream, mapping and unmap history and added boundary tests. Committing a fresh zero page on fault might let that instruction return but the stream would still be reading past its valid end. The investigation moved upstream to the I/O path. `339c26d` fixed packed APR record overflow, save-memory error and short-read handling, and I/O racing a remap. These were demonstrable contract violations. The record does not trace each bad pointer back to one particular malformed APR record.

After the corrupted pointers on the mprotect tour, `8d0c5fc` promoted uffd and fixed two fallback races plus a label-wait registration gap. Consider what the newer tracker does if a query sees more returned regions than fit in one kernel response. It resumes from the kernel's `walk_end` until the whole requested range is covered. The test with alternating writes over 1,024 pages forces more than 128 disjoint regions. The code checks forward progress and validates returned extents. If a later partial scan fails, earlier dirty indications may already have been harvested and reset. The failure path conservatively marks the entire request dirty for another attempt. Calling it clean would lose potentially the only record of a CPU write. [Scan, fallback and stress cases](../../crates/runtime/src/platform/linux/write_watch.rs)

Explicit host writers solve a related race. The uffd tracker registers guest views, leaving the GPU's aliases unprotected. The host-write journal records dirty ranges and counts active writers. The planner includes *still-active* overlapping writers in a take, and completion journals the range again. An intermediate take cannot consume the only announcement and declare the second half of a staged copy clean. The concurrency test coordinates four guest writers, alias write-back and a scanner. The full-tour result tests broader integration; that stress case tests a particular ordering a finite tour might never happen to exercise.

Merge `d91a8b0` carried seventeen further upstream commits into the platform split. The wide-render cap now had to coexist with distinct frame-generation input and output sizes, upscaler playback fixes with shared recording helpers, and the Windows hang diagnostic with Linux thread sampling. The fork's Linux notes folded these maintenance constraints into the player and developer documentation. Merging the same change literally into a Windows entry point would not have given Linux those behaviors.

### 25 November — isolating a bright real image, then counting fresh display images

The checker in `d3e1067` used a fixed save, an existing executable and fixed guest flip numbers. It measured the real colour buffer with FG disabled. That removed the interpolation adapter, viewer alpha and compositor's choice of a repeated image as explanations for the sampled brightness. `ebc3944` separated fast-clear ownership transfer for colour and depth and tested a candidate invalidation when a metadata binding changed. This made it possible to alter the ownership rule without simultaneously disabling normal metadata clears. `e4d2ae6` recorded mean colour of about 0.60 with colour handoff and 0.07 without. Depth handoff alone was fine. The default changed only for colour on Linux. The unit test for stale attachment memoization and the scene comparison answer different questions. The precise mechanism of this colour fault remains unsettled.

`418f727` introduced per-second telemetry and a three-case Nexus check. It began retiring completed old-size snapshots and trialed display-rate adaptive pacing. It initially omitted present-ID and present-wait from pipeline compatibility. The follow-up `0e64808` restored compatibility against the *actual* enabled features and configured the test process to match preparation. A single refusal then replaced the offending binary rather than disabling use of the entire store. Validation also uncovered a separate vertex-to-fragment interface mismatch. The vertex stage was updated to supply the inputs. Correct cache reuse cannot repair an invalid interface stored faithfully.

The resulting warm stationary Nexus window had zero source pipeline creations, about 260 before. In the adaptive trial content age at the median was 38 ms. Empty display slots retained the previous image without another submit and synchronous capture dumps were excluded from timed runs. These details matter when reporting “60 fresh images/s.” A generated image can count as fresh, a compositor-held buffer can age despite no extra application submission, and a good stationary store-hit rate does not promise a hitch-free first encounter elsewhere. [Nexus test design](../linux-nexus-check.md)

### 25 November — finding where parallelism stopped helping

With the watch mutex held over all scans, the recording threads serialized even when inspecting unrelated ranges. Commit `f83f06a` split each take into planning under the watch mutex and kernel scans under the already-existing shared mapping guard. This leaves mapping changes exclusive while allowing several readers to enter the kernel at once. Measuring this again requires distinguishing three clocks. Time spent waiting for the userspace mutex, kernel time spent traversing mappings, and time waiting for the exclusive remap guard can all appear to a caller as one slow placement. Approximately 7,300 takes per Palace flip and 99% empty results measured the frequency and yield of the operation. The later 370,000 scans per second were a separate observation across active workers. A take can scan more than one interval. Dividing the latter number by the former would not establish a measured frame rate.

Commit `7a5b73c` split `gpu-gfx` wait windows by cause. At native 4K with FG off, uncapped and all twenty CPUs available, it measured about 39 fps with 5 ms per frame waiting on slots whose device work was still running. Giving the main recorder a full-size chunk slowed it to 35.4. Sixteen slots gave 38.7, and the GPU-chains candidate ended the runtime. In `ce5a2de` overrides were applied *after* case defaults so that a requested change of render size really reached the process. At 1920×1080 the result was about 46 fps versus 39 at 4K. Raising submit coalescing from sixteen to 32 gave 38.2, essentially unchanged in the comparison. These data support a device limit in that configuration while leaving substantial resolution-independent work. The earlier Windows vista result is a different scene and date.

Changing anti-aliasing exposed an edge case in the adaptive presenter. With the title's TAA switched off, its depth, motion and camera snapshot never arrived. History reset on every later frame but the display scheduler still delayed real images for interpolations that would never arrive. A player went from 60 shown to 30–45 with repeats. Commit `0479087` kept the TAA input path active under FG and dropped the playback lag after three packets without an interpolation, restoring it when one returned. In the adaptive Palace test it delivered about 35 real and 25 generated images per second with no gameplay repeats. That is a different failure from an expensive interpolation that actually executes.

A crash journal has to distinguish a known driver fault from a killed test. `0084b1d` gave interrupted pipeline creations three attempts total, keeping confirmed failures and duplicate in-process creation covered. Otherwise missing draws persisted across ordinary shutdowns. Commit `5b2b610` exposed the FE2 caller census to the checker so placements could be attributed to the call paths requesting them. It records a new measurement control and no standalone speed gain.

### 25–26 November — two refreshes per movie frame and a false C4 capability

The Bink assets for the studio logo, attract movie, title logo and menu background are 3840×2160 at 30/1. Uncapped guest flips arrived at roughly 85/s for the logo and 44/s for the attract movie. At 60 Hz a frame might stay visible for one, two or three refreshes, and the FG path tried to interpolate the movie. `b4efb51` used the Bink I/O thread's lifetime to recognize movie playback, paced it at the source rate and suppressed generation during the movie. In the windowed 60 Hz check, 446 of 449 attract frames occupied exactly two refreshes. Three exceptions remain in that count. This directly tests cadence rather than inferring smooth video from an average around thirty.

The optional page armer in `9ca5b66` reduced CPU time on the graphics thread from 23.1 to 18.5 ms in the cited Palace experiment. Protect-before-use alone is insufficient. The implementation publishes its armed bit *before* installing read-only protection so a fault never arrives on a protected page with no owner. On disarm it reverses the order. Linux's signal frame leaves the interrupted red zone intact, so the handler can admit an armed write, restore permission and post to a lock-free ring without a debugger taking over the process. A concurrent remap is precisely when that shortcut must defer. A handler answering against an old mapping could make an unrelated new allocation writable. [Linux arming interface](../../crates/runtime/src/platform/linux/hosted.rs)

The first implementation accidentally changed shader generation. C4's enable test followed the fact that hosted arming was active. On Linux the armer provided no held-page release service, but C5 still emitted held-page mark logic. In one 2.5-minute session 3,412 pipelines were made again under changed fingerprints. `d41b72b` separated those capabilities. In a separate back-to-back comparison under background load with arming on, the two runs had zero store misses in both arms and measured 33.1 then 39.3 fps. The zero misses are important: that particular timing does not measure the avoided cold compiles from the previous observation. It measures how the paths behaved once their stores were warm.

Short-lived oversized glows and vertex explosions rarely coincided with the old fifteen-second screenshot interval. Commit `8c38b7a` shortened diagnostic captures to five seconds by default with an override. Each 4K image was about 18 MB. This sampling improves the chance of preserving a visible defect but introduces readback and storage work; the performance protocols use controlled captures. Commit `0722a04` made the fork's README distinguish its experimental Linux status and one tested NVIDIA PC from the Windows project's player-facing feature and performance claims.

### 26 November — diagnosing a cache collision and a mapping convoy

In `200bc91` the key used to *find* a pipeline file was coarser than the fingerprint used to *accept* its contents. Suppose session A populates a primary file and session B requests the same key with different generated code. Rejecting A's binary is correct. Replacing the primary file with B's and forgetting A creates a loop on subsequent launches. The fix keeps the other creation fingerprint in a sibling `<kind><key>.<fingerprint>.pb`, tries it when the primary is missing or holds different code, prunes it under the same budget, and counts variant hits and captures. The salted-code test deliberately creates the collision and checks reads in both configurations. The recorded 83 seconds is cumulative compilation across 49 particle programs. The 13-second freeze is elapsed time on a dependent frame. Counting them as two independent delays would misdescribe the incident.

The scan improvement had moved contention into the kernel. At about 370,000 pagemap scans per second readers kept the process memory-map lock busy. A thread creating or reprotecting a mapping needed the kernel's write side and in the observed workload could spend about 4 ms waiting for a handover. While it waited it held the runtime's exclusive remap guard. Other workers then stalled before they could even *start* their nominally independent one-page checks. Four simultaneous 107–108 ms waits were evidence of this convoy, not evidence that checking one page normally costs a tenth of a second.

Commit `21a0f16` reduced how often the writer had to re-enter that competition. A view normally arrives through one `mmap` at final protection. It temporarily needs write permission when stale bytes must be cleared. The previous map, commit, reprotect and alias operations could require four or five kernel calls under the guard. Long holds became named hitch causes and counters separated waiting for the guard from time holding it. Both old/new Palace pairs improved, with different magnitudes. The evidence identifies repeated write-side acquisition as a practical cost and reduces its frequency. It does not establish a bound on kernel writer delay under other workloads.

### 26 November — testing a texture-streaming explanation at the actual branch tip

The last commit, `0ee206e`, starts with a plausible visual hypothesis. A texture may have several mip levels, some with no resident texels yet. If the game says to sample no finer than a given level and the renderer ignores that limit, the visible result might be a black surface. The T# decoder already extracted bits 8–19 of word one. They encode a 4.8 fixed-point minimum LOD, so the raw value divided by 256 gives the level. The Vulkan image view had never applied it.

On devices with `VK_EXT_image_view_min_lod` the new sampled view supplies the limit, bounded by the available image levels. Storage views omit it. The view-cache key includes the encoded limit because a single texture can be rebound with different clamps as its mips arrive. The extension is enabled after computing the pipeline compatibility identity. Here the changed object is a view. Neither the shader nor the pipeline itself changes merely because this view extension is enabled. A test with `DS_VIEW_MIN_LOD=0` can disable it independently.

The same change decoded MIMG TFE/LWE bits 16–17 and warns when translation encounters a request whose residency status it does not write. That gives three independently observable routes to a missing-level explanation: a bound T# with a nonzero clamp, a shader instruction using its explicit clamp, or a shader asking for residency feedback. The Palace replay translated all 1,536 shaders fresh with `DS_TRCACHE=0`. No sampled view was made with a nonzero minimum, no translated instruction used the `_cl` clamp and none set TFE/LWE.
