# 1. The machine the game expects

Imagine the game loading a mesh. Its CPU code opens a file, allocates memory, asks for bytes to arrive there, and waits for completion. It writes the mesh address into a graphics descriptor and passes a list of commands to the graphics driver. Later it can reuse the allocation. Every step assumes something about the console. A successful file read has to mean the final bytes are visible. The descriptor must still refer to those bytes when the GPU draws. The signal that permits reuse must come after that draw.

## What native execution buys

The PS5 CPU and the target PC both execute x86-64. Once a code page occupies its expected address, the PC can fetch the guest instruction, perform its arithmetic and follow its branch directly. A pointer in a guest register can be dereferenced by an ordinary machine instruction. Game logic, streaming workers and animation therefore run as the original program. The input is a specific release, PPSA01341 version 01.007.000, comprising the user's data, decrypted executable and two decrypted libraries. Its identity matters because some executable patches refer to particular code sites. [How it works](../how-it-works.md) · [Required files](../install.md)

The instruction set is only one agreement between a binary and a machine. A thread also expects its private variables at particular offsets, a stack with the right layout, and library calls with particular arguments, return values and side effects. The loader adjusts supported thread-local accesses and can rewrite AMD SSE4A instructions on processors lacking them. A port can thus execute the CPU program directly while adapting specific instructions whose assumptions differ. Windows and Linux need different machinery even on the same processor.

## What replaces the console OS

High-level emulation (HLE) implements the interface the game calls. When a guest thread waits on an event, the host must remember the event state, sleep or wake the right thread, and preserve the result the guest API promises. A file or save service must translate names and implement completion and persistence. An offline service may supply enough state for “Continue Offline” without implementing a network service. The guest still runs its own higher-level systems on top. For example, the Bink workers drive movie video and shader uploads while audio samples reach the host through AudioOut. [System library implementations](../../crates/runtime/src/hle/libs) · [Movie diagnostics](../linux-play-diagnostics.md)

VideoOut gives the game a way to register output buffers, request a flip to a finished buffer and observe display timing. The host must turn that into an image the window system can show. Similarly, controller polling must return button and stick states in the game's format, and guest audio buffers need a device consuming samples at the expected rate. On Linux, closing the window flushes completed save operations. An operation still in flight has a different persistence guarantee. [Linux controls, sound and saves](../linux.md)

## Why graphics is a second translation problem

The game writes packets in AMD's PM4 command language. Some change a register, others tell a queue to draw or dispatch a compute shader, copy memory or wait for a value. A draw can inherit state set many packets earlier. Regaliant reads the packets in order and constructs Vulkan work for the host GPU. The small programs named by those packets are written in AMD RDNA machine instructions. A second translator emits SPIR-V, Vulkan's shader intermediate representation. The host driver compiles the resulting shader plus pipeline state for the actual card. A CPU instruction, a PM4 packet and an RDNA instruction consequently have three different paths through the port. [Command processor](../../crates/runtime/src/gpu/cp.rs) · [RDNA translator](../../crates/rdna/src/translate)

Return to the mesh. A discrete GPU benefits from keeping its buffers in local video memory. If the CPU changes a vertex after an earlier draw, a cached GPU copy can become stale. Conversely, a compute shader might change just one 32-bit word in a buffer the CPU can also access. Copying the whole old page back could overwrite unrelated CPU work. The runtime tracks CPU changes by page, marks individual GPU-written words and orders transfers around queue dependencies. A label, a value one participant writes for another to wait on, makes ordering visible to the game. Equality of addresses alone cannot guarantee freshness. [Front-end coherence protocol](../../crates/runtime/src/gpu/fe2.rs)


## Loading a program that contains unfinished addresses

Consider the reference that will eventually call the kernel's sleep function. On disk the game can say *which* library function it needs. It cannot know the address of a Rust function in a future process. There is also a more mundane address problem. A pointer from a module into its own data has to point to the place where that module ended up. The ELF loader solves both problems before ordinary game instructions rely on those addresses.

Start in `loader::load_bytes`. For a supported SELF container it first calls the shared `decrypted_elf` routine to rebuild the ELF from the supplied segments. A file can thus contain already decrypted executable bytes and still need unpacking into the layout expected by the ELF parser. A raw ELF skips that step. The parser supplies a *program header* for each relevant segment. The runtime computes the image span and reserves an additional 64 KiB for trampolines, small pieces of executable code to which a patched instruction can transfer control. It puts the main executable at the designated module base and finds an aligned free range for a subsequent library. An executable segment's address in the new process is the module base plus the segment's ELF virtual address. The loader copies the file-backed contents there while the image is writable. A segment can occupy more bytes in memory than its initialized contents occupy on disk. Extent and copy length have different jobs. [Loader](../../crates/runtime/src/loader.rs) · [Container handling](../../crates/dsconfig/src/self_file.rs)

Other headers describe things the loader must remember for later. `PT_TLS` identifies the template and alignment for thread-local variables. A process-parameter header locates startup data. The dynamic-link metadata describes symbols and relocations, including separate entries for the procedure linkage table, through which a call can go indirectly to its final destination. For an exported symbol defined in this image, the loader can already compute its own answer as base plus symbol value. It records nonlocal exports by library and name ID so other loaded modules can find them.

**Worked example — filling two different pointer slots.** In `relocate`, let B stand for the chosen base and R for the relocation's offset. Each iteration writes at B + R. For a `RELATIVE` relocation whose addend is A, the value written is B + A. Subsequent guest code can load that word as a pointer into the relocated image. For a `JUMP_SLOT`, the value is instead the resolved address of the indicated symbol. A later indirect call through that slot goes directly to that address. The loop covers ordinary and procedure linkage relocations, caches resolutions by symbol index, and reports unsupported relocation types. `R64` adds the relocation's addend to the symbol value. TLS relocations can install a module index or an offset relative to the thread pointer, since a global absolute pointer would give every thread the same private variable. These are the actual branches of the loop. B, R and A here stand for the fields it uses, without assuming a particular dump's addresses. [Relocation cases](../../crates/runtime/src/loader.rs)

**Worked example — binding a kernel import.** The HLE time module registers `sceKernelUsleep`. The registry hashes the function name with the fixed NID salt using SHA-1, reads the first eight digest bytes as a little-endian integer, and encodes that value into eleven characters with the console alphabet. On the importing side, a symbol has the form `NID#L#M`. The loader decodes L and uses the importing module's dynamic library table to find the library name. It looks for a matching library and NID among exports of loaded guest modules first, then in HLE. It also has a specific fallback from `libSceLibcInternal` to matching exports of the game's `libc.prx`. A remaining weak import can resolve to zero. An unresolved strong import is counted and receives a diagnostic stub appropriate to a function or data object. Enough imports resolving for boot establishes only that the paths taken so far can run. A later scene may exercise an unresolved operation for the first time. [NID encoding](../../crates/sce-elf/src/nid.rs) · [Kernel time functions](../../crates/runtime/src/hle/kernel/time.rs) · [Loader lookup order](../../crates/runtime/src/loader.rs)

## Crossing the kernel boundary and switching threads

Once bound, a call to `sceKernelUsleep` follows the guest calling convention into a host implementation that accepts microseconds, performs the sleep operation and returns the guest result. That is how a service that feels like an OS call to the game can be an ordinary function call in the host process. Raw machine instructions for entering the guest kernel require different treatment. The patcher replaces recognized raw `syscall` sites with `ud2`, a deliberately invalid instruction. Leaving such instructions intact could dispatch the number and arguments into the host kernel's unrelated syscall table. The presence of this guard is no evidence that arbitrary console syscalls have implementations. [Instruction patcher and its trap test](../../crates/runtime/src/patch.rs)

A host thread entering guest code needs a native stack, the right calling convention and a private instance of the guest TLS layout. The host scheduler can then run this thread just as it schedules the renderer's own workers. One game thread blocking on an event need not stop a second from issuing a draw or finishing a read. A fiber has a different lifetime. The game can switch saved execution contexts, including their stacks, on a thread it already has. Code that looks up the active stack's bounds must follow such switches as well.

**Worked example — joining a real guest entry.** The Linux thread test creates eight guest thread records, supplies values 40 through 47 to the same `extern "sysv64"` entry, and requests a 1 MiB stack. Inside the entry an actual x86 load reads `gs:[0x1480]`. The result must match the current `GuestThread`'s thread pointer and the self pointer at that address. The entry allocates a host vector while guest storage is active. Odd inputs take the explicit guest exit path, even inputs return normally, and joining each thread must produce its input plus one. This exercises calling, thread identity, host allocation and result delivery together. A test that simply spawned eight ordinary Rust closures would miss the central issue. [Thread test](../../crates/runtime/src/platform/linux/thread.rs)

The original guest expects FS-relative accesses. Linux already relies on FS for libc and Rust. Regaliant patches supported forms and installs a GS binding separately on every host thread that enters the guest. `Binding::new` preserves the previous GS base, obtains the pthread stack bounds, places the bounds in the per-thread area and installs that area with `arch_prctl`. The guest pointer occupies the slot at offset 0x1480. Destruction restores the previous GS base before freeing the area. The TLS test samples the host FS base before and after, reads the GS slot from assembly, and also calls back into host facilities. In a fault handler or an HLE function a host allocation still has to find the host's thread data. Switching FS only at obvious calls would leave an asynchronous signal with a much harder problem. [Per-thread binding](../../crates/runtime/src/platform/linux/tls.rs) · [Shared TLS layout](../../crates/runtime/src/tls.rs)

## Allocating bytes, mapping bytes and borrowing them for the GPU

**Worked example — follow the outputs of two guest calls.** `sceKernelAllocateMainDirectMemory` delegates to `sceKernelAllocateDirectMemory` with the whole modeled direct-memory range available. The output is a physical offset. A subsequent `sceKernelMapDirectMemory` accepts a physical offset, a length, alignment, flags and protections, and supplies a guest virtual address. Only the latter belongs in an ordinary CPU pointer. In contrast, `sceKernelMapFlexibleMemory` takes no physical offset from its caller. It asks the memory manager for a virtual mapping with backing managed on its behalf. This distinction becomes visible when the guest unmaps a direct range while keeping its physical allocation. It is entitled to map those same bytes somewhere else. [Guest-facing memory calls](../../crates/runtime/src/hle/kernel/memory.rs)

The historical implementation made the cost of getting this wrong measurable. At the gate, 3,450 nonzero pages were found among remapped ranges. Over a tour the game remapped roughly 8 GB. A workaround saved nonzero pages by physical identity on unmap and copied them back at the next map (`f3b1f83`). That can model persistence across *successive* mappings. If two addresses simultaneously refer to the same memory, copying each a private initial image immediately creates two independently writable versions. Section views solve that problem by mapping the same backing offset for both. The direct section uses the physical offset as its backing offset. Flexible memory and other non-direct mappings use a separate offset allocator.

There is another kind of alias. Regaliant can deliberately create an extra view only for the renderer. The Linux implementation maps the same memory-backed file through two host addresses. Protecting one address changes how the CPU may use that mapping while the unprotected address remains importable. A Vulkan import refers to an address range whose lifetime can extend past the guest's next unmap. In `sections::alias_unref` both remaining references and import coverage matter. A new mapping at the old guest address may occupy another alias slot. Keeping that old alias alive protects yesterday's in-flight work from seeing today's allocation. It does not give today's placement permission to reuse yesterday's mapping lookup. [Section ownership](../../crates/runtime/src/sections.rs)

## Reading a packet stream with a pencil

**Worked example — the command processor's cursor.** Read a 32-bit header at the current guest address. In the normal type-3 case bits 8–15 give the opcode and bits 16–29 encode the payload length minus one. A count field of two therefore describes three following dwords. Including the header, the next packet begins sixteen bytes later. The all-ones count field is treated specially as a header-only no-op. The walker checks the span before consuming a payload. Type 2 advances by one word. The type-0 case in this walker skips its encoded span and records the skip. Those are details of the implemented path, important when comparing a disassembly with a trace. [Packet walk](../../crates/runtime/src/gpu/cp.rs)

What the cursor does next depends on the opcode. A register-write packet changes the CP's state. It can have no immediate visible effect and still change every pixel of a later draw. For `INDIRECT_BUFFER` the CP assembles the target address from two payload words, masking the low alignment bits, and extracts the size from the low twenty bits of the third word. With bit 20 set it returns a chain to the new stream. Otherwise it calls the walker on the nested buffer and can continue the parent after it. `REWIND` can stall the parser until the CPU marks a packet valid. Thus the sequence of bytes a capture stores and the sequence of actions actually executed need not be identical. A planner that merely counted draws in the top-level buffer could miss an entire nested pass, or run past a wait whose producer is still building the next commands. [Control-flow cases](../../crates/runtime/src/gpu/cp.rs)

## Three descriptors a shader can consume

The symbol “#” belongs to the graphics vocabulary. A descriptor is a small packed record telling the GPU how to interpret something else in memory. It can reach a shader in scalar registers or through a table. Solving an address often requires knowing both the instruction that asked for a resource and the descriptor that happened to be bound on this draw.

**V# — a buffer.** The captured fill-kernel test decodes the four words `f6670000 00100010 00000800 0004bfac`. The low address word and high address bits produce base `0x10_f667_0000`. Word one also encodes a 16-byte stride. Word two gives 0x800 records, so the extent is 0x8000 bytes. Format 75 and destination selection 0xFAC describe the four-component data and its component ordering. Record twelve starts 192 bytes from the base. The decoder distinguishes byte extent from the bounds check requested by the descriptor. A zero stride uses the record count as a byte count, while the unchecked mode reports no byte-size check. Assuming every descriptor described an array of equally sized vertices would already fail this small exercise. [Captured descriptor test](../../crates/runtime/src/gpu/desc.rs)

**T# — an image.** Eight words describe the base address, format, dimensions, type, component selection, tiling and mip range. Width spans fields in two words, and both width and height store the dimension minus one. Mip levels are progressively smaller representations of the texture. Addressing a particular texel requires knowing the layout and which layer or cube face an instruction means. In the cube-array failure the descriptor selected a cube array and the operation requested an exact load. Emitting a Vulkan cube fetch gave invalid SPIR-V. The corrected load gets a 2D-array view of the same image, with layer equal to six times the cube index plus the face. A filtered directional sample in the same program still uses the cube view. The bytes need not move merely because two operations need different ways of addressing them. [Image descriptor](../../crates/runtime/src/gpu/desc.rs) · [Cube investigation](../linux-cube-fetch.md)

**S# — a sampler.** Given coordinates and a T#, the sampling instruction still needs rules for positions between texels, between mip levels and outside the image. `Images::sampler` reads those rules from four words. For example, address mode zero repeats in the chosen axis and mode two clamps to the edge. A mip filter field of two selects linear interpolation between levels. The signed LOD bias and minimum/maximum LOD limits are scaled in units of 1/256. The sampler cache keys the original words, comparison use and the PC anisotropy choice. A depth comparison and a surface-colour sample can consequently request different host sampler behavior. The T# also has its own minimum LOD. Conflating that per-view limit with the S# limit would lose a property of the image binding when a sampler is reused. Commit `0ee206e` added the view clamp. [Sampler construction](../../crates/runtime/src/gpu/images.rs) · [Linux investigation](04-linux.md)

## Translating the meaning of a shader

The decoder turns words into instructions with operands and modifiers. Scalar provenance analysis follows values back to a source, for example a register set by the CP, a pointer assembled in shader code or a load through that pointer. At draw or dispatch time the front end resolves that plan using the actual user data, descriptors and accessible memory. From the resulting specialization the translator knows such things as the stage, numeric class and image dimension for a binding. It emits SPIR-V operations, variables, control flow and resource declarations. The result still needs compatible host descriptor layouts, attachments and a driver-created pipeline. Reusing decoded instructions, reusing a SPIR-V module and reusing the finished pipeline avoid three different costs. [Analysis](../../crates/rdna/src/analysis.rs) · [Specialization](../../crates/runtime/src/gpu/shaders.rs) · [Emission](../../crates/rdna/src/translate/mod.rs)

**Worked example — why Outpost Passage showed a grid of light.** The tile-classification shader in `85664c1` grouped work by wave. Lanes first classified tiles. One elected lane counted bits and performed an atomic add to reserve a range in a shared list. The other lanes obtained the returned base index and added their own prefix counts to find individual slots. In the early translation that modeled each lane separately, the masks contained only that lane's bit. Electing the literal lane zero then let only that lane append. The light lists were mostly zero and just one tile per 64×64 pixels lit up. A generic inversion of a compare or a brighter exposure would have left the list corrupt.

The change recognized the constrained election pattern, including how the count was computed and how the atomic result crossed lanes, and arranged for each lane in that translation to reserve its own slot. A different kernel that used a cross-lane sum retained its actual election. A second fault in the same commit prevented resolution of in-code descriptors when a literal was the first operand in the address addition. The floor draws and seven compute shaders had been skipped. One scene therefore required two independent corrections. The first concerns collective execution. The second concerns discovering the shader's resources before executing it. Their shared symptom was missing light. That history explains why the project keeps both a decoder and analysis, an interpreter for comparisons, and tests of particular shader idioms. [Decoder and interpreter](../../crates/rdna/src) · [October history](03a-boot.md)

## Keeping two machines' views of a page consistent

**Worked example — two writers and one later binding.** Consider a page containing a guest CPU parameter in one word and a shader result in another. A bind that sees a new CPU parameter needs to upload it. If the GPU already updated the second word in an earlier batch, an upload copied from guest memory *before* the previous result reached guest memory could restore the old shader result to the mirror. Conversely, copying the mirror's entire page back could overwrite the newer CPU parameter. The front end orders upload prologues after earlier write-backs and marks GPU-written dwords. This is the problem the `mirror_scatter` kernel and FE2's upload bookkeeping are solving. There is no promised ordering for genuinely unsynchronized competing writes to the same word. [FE2 protocol](../../crates/runtime/src/gpu/fe2.rs) · [Write-back kernels](../../crates/rdna/src/kernels.rs)

Follow a subsequent request to bind this range. The **placement** answers where it will be bound and what must happen before this use. It can reuse a memo only if the mapping and visibility assumptions still apply. The **take** answers which CPU pages changed since dirty information was last consumed. A consumer that clears evidence must invalidate those pages for other consumers too. The **epoch** supplies a limit on how long a clean result is evidence. FE2 samples it before querying and stamps clean pages. A compute queue with its own known synchronization point and a graphics worker at a later point cannot simply assume the same answer. An **armed** page supplies stronger continuing evidence. Its read-only guest mapping ensures a subsequent CPU store faults and withdraws the proof. Quiet pages can therefore survive an epoch change without another scan.

A real error in `1f22fa1` shows how small the difference between correct and almost correct can be. Graphics stored a page and remembered its hash. Compute subsequently changed guest memory through its own write-back. Later the graphics result happened to hash to its original value again. The graphics family's local history made skipping the write look safe, but the CPU-visible copy held compute's intervening value. Invalidating the sibling family's hash repaired that case. Asking “has *my* output changed?” only suffices when the identity of the last visible writer is also known. [Cross-queue history](03c-coherence.md)
