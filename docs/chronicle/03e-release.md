# 19–25 November — preparation, memory limits and player reports

## 19 November — finding the offending draw in the player's save

The expensive barrier that suppressed the Nexus triangles was a diagnostic. The eventual fix in `8aed236` was much narrower. The translator acquired an outlier census for vertex positions. Its results were matched in time with the flashes from the frame watch. That identified an immediate-mode 2D quad program, hash `0x753675b8fbece491`. Its vertices were read from different bytes in FE2's mirror than the ones the CPU had supplied. Recording a snapshot of the specific vertex bytes each of these draws reads gave them stable input. A UI-style quad with even one wildly wrong vertex can span a great deal of screen space. The visual size of a triangle therefore says little about the size of the guest mesh that produced it.

The original save had produced about ten flashes of at least twenty cells per 15,000 frames. Two post-fix runs of 15,000 frames each recorded zero flashes at that threshold and zero even at eight cells. Validation was clean and the 1-1 walk stayed level. Compare that result with zero flashes and a large Doran slowdown behind broad barriers the previous evening. Both interventions could suppress the symptom; only the second investigation connected an individual program, its expected input, its observed input and a fix with bounded cost. It still does not prove every other instance of stray geometry in the Linux fork has that producer.

## 19–21 November — teaching preparation what this player's driver will accept

As the renderer specialized more pipeline state, a list of known program addresses became less useful for precompilation. The preparation has to learn which images, resource types, formats and render state are encountered together. A graphics pipeline also crosses stages, so knowing a pixel program in isolation leaves questions about vertex outputs and target formats. Self-playing the game supplies real combinations. The launcher isolated its hidden saves and settings, disabled system input and audio output, and used the same store the player would later open (`605fe6c`). Drawing silently in the background is a way of exercising the rendering path. Merely starting the executable hidden would not learn that path.

On 19 November the driver on a second PC refused 259 of 262 compute binaries prepared outside the ordinary host process. Preparation moved under the host. Hidden self-play exercised a new character and a tour covering 712 views. In the recorded RTX 4090 runs those stages took 420 and 2,140 seconds. Against compute-only preparation on a fixed route, first-use graphics pipeline misses fell from 83 to 14, skipped draws from 5,746 to 181, and frames longer than 250 ms from 17 to four (`605fe6c`). Self-play supplied the concrete combinations of shaders, resources and render state a static list lacked.

The tour's order changed for a practical reason. After 1-1 the player can choose several worlds. Visiting all the first levels before all the second levels gives a time-limited preparation broad coverage of likely first sessions. `6908113` records a fresh-store run reaching all twenty levels in 3,312 seconds. It also describes testing the release zip through the launcher's actual Prepare button and watching its stage marker, rather than inferring that the packaged launcher would orchestrate the same work as a developer script. Another complete timing gave 52.6 minutes on the recorded system (`c09b788`). Neither is a deadline guaranteed to a slower machine.

Large arrival pauses remained even with functioning pipeline reuse. At 1-1 the title mapped memory frequently while two texture arrays of 138 and 184 MB were being uploaded. A global mapping-change check invalidated the GPU upload decision when an unrelated area changed, leaving CPU detiling to take 119–139 ms. The check in `55280dd` consulted the last 256 changes for overlap with the texture's own range. GPU uploads then took 68–90 ms. The first arrival frame fell from 868 to 751–768 ms. A comparison of 5,405 parts found zero differing. An optimization can remove a hundred milliseconds from a bad frame and still leave a plainly visible pause. The residual matters when interpreting “fixed stutter.”

The same investigation caught a faulty comparison. Two binaries had deleted one another's translation stores, and a driver event had left a store whose binaries were being refused. The morning's slower walk did not establish a performance regression. Sharing one directory is an effective way to control an input only if both participants interpret and preserve it identically. Later Linux measurements copied private seeds, checked binary hits and separated warm-up from the timed route for precisely this reason.

On the other side of the quality/performance decision, the team backed away from skipping fill bookkeeping. A layered-only version still flashed at 1-1 Start, with 308 large flashes. Recording every write again cost about 4% at Gatehouse Hall in an unprofiled run, 46.0 against 47.7 flips/s (`c55e703`). A metadata fill can stand in for a full-surface clear. Losing its association with the eventual draw is enough to leave an old frame's pixels visible. This work is part of the background to the fork's later colour-metadata handoff problem, though neither report establishes that the two regressions were identical.

## 22–23 November — the system that works until an allocation fails

A card with ample free VRAM can conceal a lifetime bug. The old slot code freed its current shadow or batch-start buffer before creating a larger replacement. A refused allocation then left an already recorded command referring to a destroyed object. In a 4 GB tour the driver faulted. Commit `f70c6f7` kept the old allocation alive until a replacement existed. On cards reporting less than 5.5 GB of device memory it also started images of 32 MiB or more in system memory to leave room for the sparse mirror. The constrained tour survived 70 refused shadow allocations and drew every level within the recorded comparison spread. It still recorded 39 million placements without the mirror and frame times of 34–84 ms. “Can load and render” and “can maintain 60 fps” were very different claims in this experiment.

Waiting for spare memory had its own trap. The mirror refill code originally waited on every attempt to obtain a spare block, including attempts rejected without a costly driver call. A short injected run spent 83 seconds frozen. Restricting the wait to a refill actually inside the driver reduced frozen time to eight seconds in the cited 261-second new-game stage, with no page left without backing (`1e2a647`). An allocation failure is a normal branch in the low-memory policy. The fallback must itself make forward progress, keep existing device objects alive and avoid making every other thread wait for an impossible allocation.

The low-system-RAM work exposed a similar interaction with C4. An import considered cold could still cover held pages. Dropping the import forced a release through host memory that suspended other threads. Recorded pauses ranged from 58–555 ms in a full-card boot to 34 seconds in a 16 GB scenario. A window covering held pages was therefore made ineligible for cold eviction and retained at remap. Four full-card boots and a counted 16 GB arrival had zero such releases afterward, with worst frames 117–150 ms (`802a4a7`). The final release wording deliberately avoided claiming slower loads on 16 GB: the failing session took 6:43, inside the 6:20–7:22 range of sessions without import failures. A physical 16 GB PC remained untested (`2fd99f0`).

## 24–25 November — compatibility reports test assumptions the developer PC cannot

A graphics driver's answer, the application's interpretation of it, and the actual observed effect on the screen can diverge. Windows had reports of implausible total video-memory use as well as genuinely busy cards. In issue #5 other processes accounted for 11.7 GB by Windows' count on a 12 GB card, enough to keep the image cache at half budget. The machine was GPU-bound, and its preparation had restarted ten times for video memory. Commit `773b980` logged which processes were the biggest holders when crossing additional 4 GiB thresholds. The point of adding that evidence was to distinguish a constrained card from an accounting anomaly in the next report.

Reports from RTX 50 machines also challenged assumptions learned on the RTX 4090. The game can put a NaN position in unused instance slots so the GPU discards them. A translated guard must survive host-driver optimization. Without explicit float-control modes the compiler may assume away cases the guest program uses. Commit `788f235` declared supported NaN, infinity and signed-zero preservation on designs outside the original validated configuration and updated cache fingerprints. A forced 4090 validation and tunnel run worked, but that commit itself called the explanation for remote RTX 50 reports likely rather than confirmed on the reporting cards. The fork's subgroup choice and fog classification work are additional, separately tested changes. [Versioned Windows reports](../../CHANGELOG.md)

The review process also removed plausible-sounding recoveries. A proposed present fix kept retrying swapchain creation. Each attempt could itself wait for an idle queue and there was no pause between attempts. The player's log showed presentation returning after leaving and re-entering exclusive fullscreen, so it provided little support for rebuilding the swapchain in a tight loop. There was also a partial-creation failure path in which per-image semaphores could be missing. The patch and its release note were withdrawn before 0.1.3 (`61536af`). Later a proposed custom portable-data path read text from a marker file older players might already have filled with unrelated content. It too was backed out before the 0.1.7 package (`63e6c3b`, `f425ffa`). Backward compatibility includes existing installations that the current developer would never generate from scratch.

Issue #20 illustrates a case with a well-isolated failure. Cinematic mode at a wide aspect ratio could request 7680×2160 and overrun the title's render-target pool. The failing growth request was 687.25 MiB at an out-of-memory assertion. Several smaller wide extents played in, including 3584×1512 (`491fab7`). The fix bounded internal render height for ratios wider than 16:9, covering both Visual Mode and explicit scales. Package checks repeated the user's settings path, including restarting with the saved mode (`70a87b9`, `e1474d1`, `d12fb61`). The output could still occupy the whole display. A later Linux frame-generation context therefore had to accept render-sized depth and motion alongside full-display colour.

Finally, upscaling and batching interacted across an API boundary. A saved upscaler choice could be read before the upscaler was ready and never reapplied. Even when active, a deferred SDK call had captured the original command buffer. After batch fusion the SDK received the wrong destination and DLSS faulted inside the driver within seconds. Commit `5c2a205` used the command buffer supplied at deferred playback and reapplied the saved choice when ready. Review then aligned preparation's device features with play while pinning the hidden session to TAA (`7523f5f`). The fork's merges inherited these lessons alongside the code. Keeping an SDK callback in guest command order matters just as much for Linux frame interpolation as for Windows upscaling. [Linux development](04-linux.md)

## Release boundary

The release history records different failures on players' machines. Version 0.1.1 added in-place archives (54 GB against 82 GB for the tested folder). Version 0.1.3 fixed texture-streaming statistics whose reset could overtake a read. Version 0.1.5 fixed an upscaler following a small menu preview and repeatedly allocating a 30 MB image, enough to exhaust a 16 GB card within minutes. Version 0.1.6 dealt with graphics-driver debug breaks during compilation and duplicate Vulkan device listings. In 0.1.7, wide Cinematic modes had exceeded the game's render-target pool. Windows package checks at 5376×1512 and 3584×1512 confirmed the internal height cap (`d12fb61`). Another fix supplied upscalers the actual playback command buffer when recorded batches were combined. The fork merged the 0.1.4–0.1.7 changes in `d91a8b0`. The following chapter traces its separate history beginning on 23 November. [Release notes](../../CHANGELOG.md) · [Linux history](04-linux.md)
