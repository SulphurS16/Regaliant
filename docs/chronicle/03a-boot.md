# 8–14 October — proving that a submitted frame is correct

The first commit, `e190a95`, imported the same author's MIT-licensed native-port core. This accounts for PS4 terminology still visible in some shared modules. The next functional change, `f6127a5`, adapted the ELF layout and runtime to the PS5 title. Progress can be read from the places where the executable stopped. Thread-local trampolines, fibers and asynchronous file operations got it to graphics initialization (`19cd91a`). Agc shader linkage, driver registration and VideoOut let that initialization proceed (`2a031ce`). Audio, saves and stall diagnostics got the engine to its main loop (`98ca46c`). Reaching that loop established that a substantial part of the original executable could run before there was a rendered world to see.

Agc command writers and the gfx10 PM4 processor exposed the submitted frame loop (`c9fcb7a`). A decoder and frame capture made shader instructions inspectable (`c6afc48`). Analysis followed scalar values back to their sources (`5eaf976`), and the translator emitted SPIR-V (`60a9f9d`). Compute ran on Vulkan first (`7310da5`), then textures, storage images and tiling arrived (`12e451e`). Draw pipelines, render targets and presentation followed in `4b7eac6`. Reading pixels back from the swapchain verified the windowed menu in `86b1bd0`. That last observation tested more than successful shader compilation. It tested whether the displayed image actually contained the expected result.

## 8–9 October — six correct decode shaders and a movie that still smeared

Movie decoding provided an unusual opportunity. A recognizable frame was helpful, but correctness could be tested much more precisely. The CPU reference interpreter in `6ed4bb8` executed a gfx10 workgroup according to the documented instruction semantics independently of SPIR-V emission. The developers could feed the interpreter a dispatch and compare its outputs with the translated shader on a GPU. They could also dump registers at a particular instruction. This turned “the movie looks wrong” into a sequence of smaller questions. Do the invocations branch together? Does a lane see the value another lane just wrote? At which instruction do register results diverge?

The Bink decoder and more than thirty shaders in a captured frame used local data share (LDS), the on-chip memory through which lanes exchange values. They relied on wave execution order without spelling out a workgroup barrier at every exchange. Regaliant's lockstep mode used a workgroup vote for lane-dependent branches in eligible programs and inserted synchronization where one lane could read another's earlier access. Other corrections in the same commit made an image gather fill four vector registers irrespective of the component mask and prevented contraction of floating-point operations that should round twice. After those changes all six Bink shaders matched the interpreter on every tested workgroup. One comparison covered 8.3 million luma texels with zero differences.

Motion still smeared until the next keyframe. The guest reused a movie slot roughly 1.6 ms after its GPU work started. The host CP could start a command buffer much earlier than the translated dispatch actually consumed its memory. The code copied short command buffers, up to 512 dwords, when the CP started them. An artificial 30 ms delay could produce exact output. Synchronous small submissions mostly corrected it at about half the frame rate. There was also an intermittent fault in three of roughly thirty runs. The shader comparisons had removed one explanation while leaving queue timing and buffer lifetime squarely in view. A modern screenshot of a correct movie would tell very little about how these faults were distinguished. [Reference interpreter](../../crates/rdna/src/emu.rs)

## 9–10 October — reconstructing a room from the draws that should have built it

Outpost Passage made an instructive test scene. The missing geometry was not a single missing model. `b5c463d` found that the title indexed instance data using a user scalar register plus the instance ID. Certain indirect draws provided no start-instance scalar register. Without supplying the value as Vulkan's first instance, every culled draw used instance zero's transform. A draw could execute, sample valid data and nevertheless put an object at somebody else's location. The same change corrected the multi-draw packet layout. Its flags word had been interpreted as a draw count. The tunnel's walls and ceiling depended on those packets.

The lit tile grid in `85664c1` came from a wave-wide append operation that the early translator had reduced to one contributing lane. The change also let the resource analyzer follow an address formed by adding a literal on the other side of an instruction. The worked example in [first principles](01-first-principles.md) follows both errors. One useful lesson from this phase is how a skipped floor draw and a malformed light list can reinforce each other's symptoms. Fixing transforms alone cannot light a surface whose deferred lighting pass never received a correct tile index.

On 10 October `2eb3bec` found an entire class of missing work. The graphics form of an indirect dispatch takes an offset relative to a register base. The asynchronous compute form carries an address as low and high words followed by an initiator. The CP had decoded both as the graphics form. It added the low half to zero, found no mapping and silently skipped the dispatch. Every indirect dispatch on those compute queues had been lost, including parts of light-probe updates, instancing and particles. The fix selected the packet layout by queue and logged skipped dispatches. In the resulting passage the walls showed ivy, water drops appeared and the character's armour was visible. This was evidence about a whole producer chain: later shaders had been reading the plausible-looking but unproduced outputs of earlier work.

## 10–11 October — teaching the host driver to compile the translation

Early translation could express guest branches as a dispatcher selecting the next block by address. That represents arbitrary control flow but gives the host compiler a difficult optimization problem. `8856caa` identified loops whose ranges nest and whose only entry is their header. It emitted structured SPIR-V loops for them, carrying the next address through guards for exits and outer loops. Every one of the 850 shaders in the capture qualified. The 258 compute pipelines took 73 seconds to compile against 138 seconds before. Compute register use fell 18%, with the screen-space global illumination pass dropping from 128 registers to 72. All 1,142 modules validated, the 258 pipelines built and ran, and the interpreter comparisons agreed. These checks tested structural validity, driver acceptance and output separately.

On 11 October `cf37a48` separated registers into individual variables where indirect register moves did not require an indexed register array. It computed a lane's execution bit once per block. One capture shrank from 140.1 to 89.6 MiB of SPIR-V. A cold run created 1,258 pipelines in 5.7 seconds, none taking over 200 ms, where the older form had spent 103 seconds in just 166 slow compiles. The in-run performance comparison remained within noise. A player benefits because a shorter compile takes less time out of a first visit even if subsequent draws of the finished pipeline take equally long.

The same commit moved selected scalar data loads into the shader as an experiment. That eliminated a vertex-stage CPU wait for a GPU-written constant block. Yet image descriptors in that block still had to be read to prepare the same draws. The wait moved to the next consumer and frame rate held steady. Another correction allowed an equality wait to pass on a counter already beyond the requested value. The observed hang had occurred when a command buffer containing the wait reached a queue *after* the write. A completion scheme that assumes the consumer is always listening before the producer signals can work perfectly in a slow debugger and deadlock in ordinary execution.

## 11–12 October — from getting the castle back to finding grass in the fountain

The missing courtyard castle led to a temporary intervention in title code. The game set a bit on a render item when handing it from its CPU list to GPU-driven batches. Those batches drew nothing for the affected items. `4a08faa` cleared the bit at the handoff, restoring the castle on the CPU path. The developers logged the workaround and retained a switch so they could examine the broken route again. The November census of the two paths (`d539031`) measures a later implementation. The visually successful October stand-in cannot settle which route is correct once the renderer itself has changed.

In `3c242d4` the graphics command processor spent 36% of busy time searching lists of pending writes. Coalescing ranges by batch sequence avoided scanning the whole list on every overlap query. An oversized global mutex was split into read-mostly import lookup, per-thread recent hits and separate pipeline maps, with pipeline creation outside the lock. Queue lock waits fell from roughly a quarter of thread time to about 1%. The GPU-driven route improved from about 0.8 to 1.2 flips/s and around 2.0 warm. Those numbers explain why the project devoted so much subsequent work to per-command CPU cost. The machine could show the castle long before it could issue the game's intended draws at playable rates.

The fountain fault in `e0e221a` is a concrete counterexample to a tempting cache rule: “when a batch submits a copy of range X, mark X submitted.” Two batches could miss the same range simultaneously and create different copies. Publishing the range without the creator's identity let a third batch bind a copy whose own producing batch had never submitted. Grass appeared in the fountain and persisted through the run. Giving entries an ID and publishing only entries made by that batch fixed the race. The new submission thread also moved queue calls off the CP, gaining about 1.3%. Performance and correctness both depended on distinguishing a promised copy from a submitted one.

## 12–14 October — what has to stay alive during a level transition?

In `329c3b7`, a queue thread detiling a streamed 64-layer image checked that a layer was mapped, then faulted in the copy. A title thread had unmapped the layer between the check and use. Shared access for the whole upload and exclusive access for decommit or reprotection fixed this particular race. A subsequent six-level tour completed. By the next day four of six tours and three of four repeated loads had shown device loss even with the day's optimization switches off. The device could hang on a batch with no draw or dispatch. This called for looking beyond translation.

Guest buffers were imported in windows up to 64 MiB. The game could legitimately discard one allocation while live work still used a neighbouring buffer inside that import. Removing host backing from under the wider pinned range could invalidate the device's view. The latest overlapping decommits came within 0.3 s of device loss. Commit `816c1ab` deferred decommits until no live or retired-but-unfreed import covered the range. A range recommitted before physical release got the zeroing expected of fresh memory. Two load loops and two eight-level tours then completed. This is why the later sections design includes alias slots and lifetime tracking even when the guest has already forgotten the old address.

Written-buffer shadows posed the converse question: which data could survive long enough to be reused? Recopying a shadow from guest memory across PCIe cost about 3.9 ms of device work per courtyard frame. `956630e` reused the completed working copy, dating CPU writes and invalidating for CP and aliased writes. Shadow copy-in fell 30–37% across three pairs. A device-side sample found 1,832 of 1,832 copy-ins equal to guest memory. Meanwhile `f573ad2` added a detector for races involving GPU-read data. By this point the developer needed both proofs: that the bytes used for a particular operation matched the guest and that another queue would not be allowed to invalidate the premise while the operation was in flight. The [next period](03b-residency.md) made that lifetime question the center of the renderer.
